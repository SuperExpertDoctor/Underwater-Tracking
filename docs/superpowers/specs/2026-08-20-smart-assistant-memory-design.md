# 智能助理与分层记忆系统设计

- 日期：2026-08-20
- 状态：已确认，待实施计划
- 范围：专家智能助理、短期上下文、三类长期记忆、记忆检索窗口

## 1. 目标

本功能把现有的会话入口升级为“智能助理”，同时支持两条明确的人机协作路径：

1. 方案调整：专家提交反馈，助理结合当前态势、当前方案、短期上下文和有限的长期记忆素材生成方案预览；只有专家显式确认后才进入现有方案应用链路。
2. 证据回溯：专家追问方案为何形成，助理先通过记忆检索定位线索，再回到事件、决策、知识和方案版本记录，返回只读的因果解释和可验证来源，不修改当前方案。
3. 过程可视化：在主界面底部 `LLM思考过程` 旁增加 `Memory Steam` 选项，实时展示短期/长期记忆的产生、检索、压缩、版本迭代、访问和归档过程。

智能助理需要具备以下记忆能力：

- 短期上下文达到消息数或 token 阈值后由 LLM 压缩为摘要，保留关键事实、目标、已确认决策、待解决问题、偏好和证据引用。
- 长期记忆分为情景记忆（过去事件和历史对话片段）、语义记忆（静态事实、偏好、规则、知识）和程序记忆（技能、行动范式）。
- 不是所有对话都进入长期记忆；筛选、提炼、检索、演化和遗忘均有明确边界。
- 长期记忆永远不能替代短期记忆。长期记忆只能作为有限参考素材注入短期上下文，最终推理全部在短期上下文中完成。

## 2. 现有系统边界

设计复用以下既有能力，不另起一套方案或证据链：

- `ConversationContext`、`process_conversation_message` 和现有分类器继续负责方案调整/证据回溯路由。
- 方案调整继续使用“预览 -> 显式应用”的双阶段流程，不能由记忆系统直接改方案。
- 证据问答继续复用当前规划快照、事件仓库、决策账本和证据校验。
- 现有 `operational`、`decision`、`conversation` 历史摘要继续作为来源材料；它们是可追溯历史投影，不直接等同于新的三类长期记忆。
- 现有 `StructuredLLM` 是所有记忆相关 LLM 操作的唯一调用端口，操作、模型、prompt/schema 版本和 token 元数据写入既有 LLM 审计表。

系统当前没有认证层。所有新接口增加 `user_id`，缺省值为 `operator`。接入认证后，认证主体 ID 替换该默认值，但数据模型和检索边界不变。

## 3. 总体架构

新增统一的 `MemoryService`，由四个边界清晰的组件组成：

1. `ShortTermContextStore`：保存每个用户/会话的滚动摘要和有界的最近原文。
2. `LongTermMemoryRepository`：保存三类长期记忆、版本链、来源引用、访问统计和状态。
3. `MemoryReasoner`：调用结构化 LLM 完成筛选、提炼和短期压缩，并校验来源范围。
4. `MemoryRetriever`：生成查询向量，执行同用户 Top-K 召回、过滤、重排和访问统计更新。

`MemoryService` 对会话节点提供两个核心操作：

- `prepare_context(user_id, conversation_id, query, filters)`：读取短期上下文，召回有限长期素材，并构造有界的推理上下文。
- `commit_turn(turn, result)`：保存短期消息，执行记忆筛选/提炼、版本更新和必要的短期压缩。

`MemoryService` 同时向 UI 发布有界的 `MemoryStreamEvent`，用于记录记忆生命周期的可观察过程。事件是记忆审计投影，不承载未经筛选的原始 LLM 请求内容，也不改变方案执行链路。

仿真物理 tick、UUV 状态更新、任务轮转和资源轮转不调用 `MemoryService`，避免记忆逻辑拖慢长时间运行链路。记忆维护在专家消息、智能助理查询和独立的低频维护任务边界执行。

## 4. 数据模型

### 4.1 短期上下文

按 `(user_id, conversation_id)` 唯一保存：

- `summary_text`：最近压缩摘要。
- `summary_version`：短期摘要自身的递增版本。
- `recent_messages`：有界的最近消息，包含角色、文本、时间、来源证据和 turn ID。
- `message_count`、`estimated_tokens`、`compression_count`。
- `last_compressed_at`、`updated_at`、`compression_status`。

原始消息只在短期窗口中保留有限数量；已压缩内容不能通过删除原文来替代长期记忆来源。来源事件、决策和对话审计记录仍由原有持久化层保留。

### 4.2 长期记忆版本

每个逻辑记忆拥有稳定的 `memory_family_id`。每次内容更新都创建不可变新版本，不覆盖旧行：

- `memory_id`：当前版本唯一 ID。
- `memory_family_id`：同一逻辑记忆的稳定 ID。
- `version`：从 1 开始连续递增。
- `user_id`：检索和删除的强制隔离键。
- `memory_type`：`episodic`、`semantic` 或 `procedural`。
- `summary`：用于检索和上下文注入的精炼记忆。
- `importance_score`：0 到 1 的重要性分数。
- `embedding`：可检索的向量及向量版本。
- `status`：`active`、`superseded`、`archived` 或 `deleted`。
- `supersedes_memory_id`：被当前版本替代的上一版本。
- `source_message_ids`、`source_event_ids`、`source_decision_ids`、`source_knowledge_ids`。
- `change_reason`：首次创建、用户修正、事实更新、冲突解决或摘要重算。
- `created_at`、`last_accessed_at`、`access_count`、可选的 `sim_time_s`。

数据库事务保证同一 `(user_id, memory_family_id)` 只有一个最新有效版本，并保证版本号连续。旧版本进入 `superseded` 后不参与默认检索，但保留用于版本展示和证据回溯。

### 4.3 版本行为

- 新信息创建新版本，旧版本标记为 `superseded`。
- 冲突修正必须引用被修正的候选版本，不能由 LLM 构造不存在的 ID。
- 默认检索只取每个记忆族最新的 `active` 版本。
- 版本历史接口返回 `v1 -> v2 -> ...`，包括每次更新原因和来源。
- 手动删除将记忆族标记为 `deleted`，立即停止检索和 UI 展示；不删除原始对话、事件、决策和审计记录。
- 归档版本不进入上下文，但可在管理员或证据回溯视图中查询。

## 5. 单轮处理流程

专家消息进入 `/api/conversation/messages` 后按以下顺序处理：

1. 校验 `user_id`、`conversation_id`、方案版本和消息大小。
2. 加载该用户/会话的短期摘要与最近原文。
3. 使用最新消息生成查询向量，在同一 `user_id` 下检索长期记忆。
4. 先过滤 `status=active`、记忆类型、时间范围、最低重要性和每用户边界，再做 Top-K 相似度召回和重排。
5. 只取有限数量的最终记忆片段，并将它们标记为 `long_term_material` 加入短期推理上下文；不得直接把完整长期库传给 LLM。
6. 将当前态势、当前方案、短期上下文和长期素材交给会话分类/推理操作。
7. 方案调整只返回预览；证据回溯只返回回答和来源；混合请求分别返回两部分结果。
8. 保存本轮短期消息及结果。
9. 调用记忆筛选器；通过后调用记忆提炼器，按新建/更新/忽略执行长期记忆事务。
10. 达到短期消息数、token 或硬上限时调用短期压缩，保留摘要和最近原文。
11. 更新检索访问统计，并执行低频的时间衰减和归档维护。

长期记忆检索失败时，步骤 6 仍使用当前态势、当前方案和短期上下文继续执行，并返回 `memory_status=degraded`。长期记忆不可用不能改变方案调整的显式确认边界，也不能产生替代证据。

每个关键步骤都可以产生一条 `MemoryStreamEvent`，但事件数量必须受窗口上限约束。至少覆盖：

- `context_loaded`：加载短期摘要和最近原文。
- `retrieval_started`、`retrieval_completed`：记录查询范围、命中数量和最终命中版本。
- `memory_filtered`：记录保存/过滤结果和分类理由，不记录敏感原文。
- `memory_extracted`：记录提炼出的记忆族和来源引用。
- `memory_version_created`、`memory_version_superseded`：记录版本迭代及更新原因。
- `short_term_compression_started`、`short_term_compressed`、`compression_degraded`：记录短期摘要压缩状态。
- `memory_accessed`、`memory_archived`、`memory_deleted`：记录访问、演化和用户操作。
- `evidence_trace_started`、`evidence_trace_completed`：记录从记忆版本到原始证据的回溯结果。

事件必须带 `event_id`、`user_id`、时间、状态和来源 ID；`conversation_id`、`memory_id`/`memory_family_id` 及版本号按事件类型提供，维护任务事件可以没有会话 ID。事件流只返回当前用户范围内的记录，并按创建时间和模拟时间稳定排序。

## 6. 结构化 LLM 操作

### 6.1 `memory_filter`

输入当前轮、短期上下文摘要和有限候选记忆，输出：

- `should_store`、`explicit_remember`。
- `memory_type`。
- `operation`：`create`、`update` 或 `ignore`。
- 稳定的 `family_key` 或候选 `memory_id`。
- `importance_score`、标签、判定理由。
- 冲突候选版本 ID。

问候、感谢和一次性闲聊应被过滤；显式“记住这件事”优先保留。服务端校验所有候选 ID、分数、类型和用户边界。

### 6.2 `memory_extract`

输入通过筛选的原始对话和来源，输出短摘要、稳定事实/行动模式、去重后的标签、来源 ID 和 `change_reason`。摘要必须短于配置限制，不能扩展输入中不存在的事实。

### 6.3 `short_term_compress`

输入需要压缩的旧消息、既有短期摘要和来源引用，输出关键事实、目标、决策、待办、未解决问题、用户偏好和证据 ID。最近若干轮原文继续保留，摘要不能删除正在等待确认的方案预览。

### 6.4 会话推理

现有 `conversation_classification` 扩展为接收 `assistant_mode`、短期上下文和受限长期素材。输出中的 `evidence_ids`、`memory_ids` 必须属于本次提供的候选集合。证据回答需要明确区分原始事件/决策证据和长期记忆素材。

### 6.5 证据回溯

证据回溯不是直接把记忆摘要作为答案，而是执行受约束的多阶段路径：

1. 将专家问题向量化，检索同一 `user_id` 下的最新有效记忆版本。
2. 读取命中记忆携带的来源消息、事件、决策和知识 ID。
3. 通过事件仓库、决策账本、知识查询和方案版本记录验证来源仍存在且属于当前场景。
4. 构造“专家问题 -> 记忆版本 -> 来源记录 -> 方案/决策版本”的因果链。
5. 只把验证通过的原始证据 ID交给回答模型，回答中同时标记记忆素材和原始证据。

如果记忆版本存在但来源已不可解析，返回“记忆线索存在、原始证据不足”的状态，不把摘要升级为事实。每一步回溯过程写入 `MemoryStreamEvent`，供 `Memory Steam` 和回答审计使用。

LLM 操作失败时：长期筛选/提炼不写入；短期压缩保留旧摘要和硬上限内的最近消息；不会使用静态伪造回答或伪造记忆作为生产回退。

## 7. 检索、重排和演化

新增 provider-neutral 的 `EmbeddingProvider` 边界。默认实现使用稳定的本地 token/n-gram 哈希向量，存储向量版本并计算 cosine 相似度，不依赖新基础设施；后续可配置真实 Embedding Provider 替换该实现，不改变记忆表和检索接口。

默认检索策略：

- 强制 `user_id` 相等。
- 过滤类型、时间窗口、`importance_score` 下限和 `status=active`。
- 每次最多召回固定数量，重排后再按上下文 token 预算截断。
- 重排综合语义相似度、重要性、时间衰减和访问频次；最终分数和命中原因返回 UI。
- 只更新最终命中记忆的 `last_accessed_at` 与 `access_count`，不因候选扫描虚增访问量。

演化规则：

- 重要性按墙上时间缓慢衰减，仿真时间只作为来源维度保留。
- 最终命中会提升访问权重；长期未访问会降低权重。
- 新信息与既有事实冲突时创建新版本并使旧版本失效。
- 独立维护任务定期把低于归档阈值的记忆标记为 `archived`；删除策略只作用于记忆投影，不触碰原始证据。

## 8. API 与 UI

### 8.1 API

`POST /api/conversation/messages` 增加：

- `user_id: string = "operator"`
- `assistant_mode: "auto" | "plan_revision" | "evidence_query" = "auto"`

响应增加 `memory_context`：短期摘要状态、压缩状态、命中的记忆版本、检索分数、记忆状态和可引用的 `memory_ids`。

响应同时增加 `memory_stream_cursor` 和本轮新增的 `memory_stream_events`，让 UI 可以增量显示本轮记忆过程，而不必重新加载整个历史流。

新增接口：

- `GET /api/assistant/memory`：按用户和会话返回短期记忆、三类长期记忆、当前检索命中、版本号和状态；支持类型、时间、重要性和数量上限。
- `GET /api/assistant/memory/{memory_family_id}/versions`：返回一条逻辑记忆的完整版本链。
- `DELETE /api/assistant/memory/{memory_id}`：校验 `user_id` 后标记对应记忆族为 `deleted`。
- `GET /api/assistant/memory/stream`：按 `user_id`、`conversation_id` 和游标返回有界的 `MemoryStreamEvent` 增量；支持从指定时间或游标继续读取。

接口响应不包含其他用户记忆，也不把长期记忆未经筛选地暴露为推理上下文。

### 8.2 UI

用新的 `SmartAssistantPanel` 替换旧的 `ConversationPanel`/`LLM Client` 可见实现，右侧面板标题改为“智能助理”。

- 顶部使用“方案调整 / 证据回溯”分段模式控制，并保留 `auto` 兼容路径。
- 方案调整显示预览差异和显式应用动作；证据回溯显示只读回答和可点击来源。
- 记忆窗口显示“短期记忆 / 情景记忆 / 语义记忆 / 程序记忆”四个视图。
- 每条记忆显示当前版本、重要性、访问次数、最近访问时间、命中分数和来源。
- 展开一条记忆可查看版本链与更新原因；删除使用图标按钮并提供可访问名称和悬停提示。
- 首次加载、消息发送后和运行中定时刷新都调用真实后端接口；无数据显示真实空状态，网络失败显示真实错误状态。
- 应用代码和验收链路不保留 mock 记忆数据。组件级静态渲染测试只验证布局契约，真实数据行为由运行中的 FastAPI + SQLite 后端验收。

### 8.3 Memory Steam

`Memory Steam` 是主界面底部与 `LLM思考过程` 并列的选项，不替代右侧的记忆检索窗口：

- 右侧记忆窗口展示“现在有哪些记忆”，包括短期摘要、三类长期记忆、当前版本、重要性、访问次数和版本历史。
- 底部 `Memory Steam` 展示“记忆刚刚发生了什么”，按时间显示加载上下文、检索命中、筛选、提炼、压缩、创建新版本、旧版本失效、访问、归档和删除。
- 当前专家消息关联的事件高亮显示；检索命中的长期记忆显示类型、版本号、相似度和来源数量。
- 短期压缩显示摘要版本变化，例如 `short-term summary v2 -> v3`；长期更新显示 `memory family v1 -> v2`。
- 证据回溯显示一条可展开的因果链：`问题 -> 记忆版本 -> 来源事件/决策/知识 -> 方案版本`。记忆素材和原始证据使用不同标签，不混淆两者。
- LLM 或记忆服务降级时，流中显示明确的 `degraded` 事件；不伪造成功的记忆写入、检索或证据回溯。
- 流本身有数量上限和增量游标，页面切换或刷新不会导致重复事件；所有内容来自真实 `/api/assistant/memory/stream`。

## 9. 性能与可靠性

- 长期记忆查询使用索引字段 `(user_id, status, memory_type, created_at)`，并对版本、数量和上下文 token 设置硬上限。
- SQLite 写事务只包含必要的版本切换和短期上下文更新，不持有物理仿真锁。
- 维护任务不调用 LLM，低频执行衰减、访问统计整理和归档。
- 记忆系统不可用时不阻断当前态势读取、证据查询或方案预览；响应必须暴露降级状态。
- LLM 元数据只保存哈希、操作、版本、耗时和 token 数，不持久化 API key、请求头或敏感凭证。
- 所有手动删除、版本切换和归档操作保留审计事件，原始事件和决策不可变。

## 10. 测试与验收

### 后端单元和集成

- 三类记忆筛选、一次性闲聊过滤、显式记住、提炼长度和来源校验。
- 短期消息阈值、token 阈值、摘要保留和压缩失败的有界回退。
- 版本创建、连续版本号、冲突失效、最新版本检索和版本链展示。
- 相同 `user_id` 检索隔离、类型/时间/重要性过滤、Top-K、重排和访问频次。
- 时间衰减、低权重归档、用户删除和删除后的不可检索行为。
- 方案预览/显式应用与证据回溯只读边界，长期记忆不能替代短期上下文的断言。
- FastAPI 接口的默认 `operator`、用户隔离、错误响应、分页/数量上限、真实 SQLite 持久化和 Memory Stream 增量游标。

### UI 与端到端
