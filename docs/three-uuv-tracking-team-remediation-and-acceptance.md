# 三艇动态跟踪问题四人职责拆解与验收标准

## 1. 文档目的

本文将 `configs/scenario/uuv_only_single_target.yaml`、seed `42` 实际运行中发现的问题，按四位成员的职责拆分为可独立实施、可独立验收、最终可汇合成完整闭环的工作项。

四位成员分别负责：

1. 前端；
2. UUV 控制，包括区域覆盖扫描和多 UUV 协同跟踪；
3. 世界模型；
4. LLM 相关能力，包括多层记忆、LLM 智能助手和 LLM decision maker。

本文的分工原则是：

- 前端只展示后端已经确认的运行状态，不在浏览器中推断状态机；
- UUV 控制层是部署、扫描、被动跟踪、交接、替换、专属跟踪和退出的最终执行权威；
- 世界模型只基于公开估计生成预测、风险和数据健康信息，不读取真值，也不直接控制 UUV；
- LLM 只负责高层方案候选、语义解释和人机交互，不直接生成物理坐标、航点、UUV ID 或绕过确定性安全门限；
- 任一成员不能用合成状态机夹具代替普通实时仿真的最终验收。

## 2. 实测基线与总目标

### 2.1 当前基线

本次已知实测基线为：

- 场景：`configs/scenario/uuv_only_single_target.yaml`；
- seed：`42`；
- 运行长度：120 个物理步，共 600 s；
- 重复运行：2 次，轨迹摘要一致；
- UUV-only 跟踪/覆盖审计：`PASS`；
- 状态机和审计相关测试：`69 passed`；
- 用户提供的证据目录：`outputs/actual-visual-audit-20260904-short/`；
- 已有实际效果：四区域、12 艘 UUV、4 个三艇任务组均已部署并运动；
- 当前核心断点：600 s 时仍为 4 个 `ACTIVE_SCAN`，`Passive groups: 0`，`Tracking owner: none`。

### 2.2 全系统最终效果

核心发布验收必须在同一个固定 seed 的普通实时运行中完成以下闭环：

```text
四区十二艇部署
  -> 三艇执行有真实主动 ping 支持的区域扫描
  -> 公开融合估计持续更新
  -> 某区域入区概率连续两周期 >= 0.70
  -> 该组三艇原子切换为 PASSIVE_TRACK
  -> 产生唯一 tracking owner
  -> 相邻接班组三艇全部取得当周期有效被动观测
  -> owner 无空窗切换
  -> 旧组 EXITING 并在越界后 DISAPPEARED
```

该闭环通过后，才算实现状态机文档要求的核心反潜跟踪效果。区域替换和专属跟踪恢复属于第二阶段演示门禁，但仍需完成，不能用单元测试结果代替真实画面和真实 `OperationalFrame` 证据。

## 3. 问题编号与主责关系

| 编号 | 原问题 | 主责 | 必须配合 |
| --- | --- | --- | --- |
| I-01 | 执行快照过期后，旧目标估计和旧预测长期停留 | LLM、UUV 控制分别负责生成侧和准入侧 | 世界模型、前端 |
| I-02 | 已有融合估计，但未进入 `PASSIVE_TRACK` 和 owner | UUV 控制 | 世界模型、前端 |
| I-03 | 完成路线被误读为完成主动扫描覆盖 | UUV 控制 | 前端 |
| I-04 | 区域概率、确认计数、组生命周期和阻塞原因不是界面主信息 | 前端 | UUV 控制、世界模型、LLM 助手 |
| I-05 | 普通运行没有交接、替换和专属模式的实际画面 | UUV 控制 | 前端、世界模型、LLM decision maker |
| I-06 | 审计渲染与正式指挥界面语义混杂 | 前端 | 世界模型、LLM 助手 |

I-01 是一个跨模块问题，不能只指定一个人笼统负责：LLM 负责人保证在快照有效期内持续产生新候选，UUV 控制负责人保证候选能够通过确定性准入并恢复执行，世界模型负责人保证候选所依赖的公开估计和预测新鲜，前端负责人诚实展示数据年龄和失效状态。

## 4. 成员一：前端负责人

### 4.1 负责范围

主要涉及：

- `src/underwater_tracking/ui/src/`；
- `src/underwater_tracking/ui/e2e/`；
- `OperationalFrame` 的 TypeScript 契约、选择器和显示逻辑；
- 地图、状态条、侧栏、图例、回放和评估模式开关。

前端不负责修复状态机，不得读取物理真值来“补出”目标运动，也不得根据 UUV 位置自行判断 `PASSIVE_TRACK` 或 owner。

### 4.2 F-01：过期估计仍按实时目标绘制

**对应问题：I-01。**

当前画面会继续用正常样式绘制过期的 `target_estimates` 和旧预测线，导致目标看起来静止。

修复建议：

- 直接消费后端提供的估计时间、预测起点、`valid_until_s`、数据年龄和健康状态；
- 将目标数据明确区分为 `live/current`、`stale/degraded`、`expired/unavailable`；
- 估计过期时显示“目标估计已过期 / 等待刷新”、最后更新时间和数据年龄；
- 旧目标点不得继续使用 live 样式，旧预测走廊应降亮、虚化或加冻结标识；
- UUV 和仿真时钟仍继续显示当前物理帧，不能因为语义数据过期而冻结整幅地图；
- 正式运行态不允许回退显示目标真值。

个人验收效果：

- 构造一个当前帧时间大于估计有效期的 `OperationalFrame`，页面明确显示过期状态；
- 操作者可同时看到“仿真仍在运行”和“目标估计已经失效”；
- 过期目标、预测线与有效目标的样式有稳定、可测试的区别；
- 新估计到达后，状态自动恢复为 live，更新时间和数据年龄同步刷新；
- 旧回放缺少新健康字段时按 `unknown/unavailable` 处理，不错误标为 live。

### 4.3 F-02：扫描路线和扫描覆盖没有分开表达

**对应问题：I-03。**

修复建议：

- 每个区域同时显示 `路线进度`、`本轮主动覆盖`、`源支持 ping 数`；
- “航点完成”只表示路线执行完成，不得显示为“扫描完成”；
- 只有后端的覆盖率达到配置阈值，且覆盖证据来自真实主动 ping 时，才显示“本轮扫描完成”；
- 无主动 ping 时明确显示 `0 次` 和 `0%`，不能由扇形图层、航迹或航点访问率推导覆盖完成；
- 扫描轮次重启时清晰重置“本轮”统计，不混入历史累计值。

个人验收效果：

- 当航点访问率为 `1.0`、主动覆盖为 `0%` 时，页面显示“路线完成，扫描未完成”；
- 当 `task:01` 为 `25%`、其余区域为 `0%` 时，四区分别显示真实数值；
- 达到配置的 `scan_completion_threshold` 后才出现“本轮扫描完成”；
- 前端数值与同一帧后端字段完全一致，无二次计算造成的偏差。

### 4.4 F-03：状态机确认条件没有成为常驻主信息

**对应问题：I-04。**

修复建议：

- 为每个目标提供常驻状态条，而不是只在角落显示汇总数字；
- 状态条按后端字段渲染以下过程：

```text
部署 3/3
  -> 主动扫描（覆盖 xx%）
  -> 入区确认 0/2、1/2、2/2
  -> 被动跟踪（owner: Gxx）
  -> 接班被动观测 0/3、1/3、2/3、3/3
  -> owner 切换
  -> 旧组退出
  -> 旧组消失
```

- 常驻显示区域概率、连续确认次数、组生命周期、组传感器模式、当前 owner、候补组证据、incoming/outgoing 批次和阻塞原因；
- 阻塞原因必须是后端结构化原因的可读映射，不由前端猜测；
- owner 切换必须在同一帧中同时反映“新 owner”和“旧组 `EXITING`”。

个人验收效果：

- 给定后端状态序列，页面逐帧准确显示 `0/2 -> 1/2 -> 2/2 -> PASSIVE_TRACK`；
- 给定接力状态序列，页面准确显示接班组 `0/3 -> 3/3`、owner 切换和旧组退出；
- 缺失观测、概率不足、预测离区、部署不完整等原因均能显示；
- 页面不产生后端不存在的 owner、确认次数或生命周期。

### 4.5 F-04：缺少交接、替换和专属模式的正式画面

**对应问题：I-05。**

修复建议：

- 为 `PASSIVE_TRACK` owner 提供清晰且唯一的视觉标识；
- 在交接期间同时呈现旧 owner、新候补组、三艇被动观测进度和退出路线；
- 区域替换期间同时呈现 incoming/outgoing 组、执行 revision、几何 revision 和部署批次；
- 专属模式显示 `DEDICATED_TRACK`、剩余里程最低值、`7000m` 阈值和 `DEDICATED_RELEASE_PENDING`；
- 旧组只有收到 `DISAPPEARED` 后才从画面移除，不能在 owner 切换时立即消失。

个人验收效果：

- 能从普通实时运行中保存扫描、首次跟踪、接力、替换/专属恢复四类关键帧；
- 每张图中的状态、组 ID、UUV 数量、owner 和 revision 与同期 `OperationalFrame` 一致；
- 交接画面不存在两个 owner，也不存在 owner 空窗；
- incoming/outgoing 并存时不会因临时超过 12 艘 UUV 而隐藏合法执行组。

### 4.6 F-05：正式指挥界面与评估模式分离

**对应问题：I-06。**

修复建议：

- 正式模式保留公开估计、置信度、预测、区域、覆盖和三艇状态；
- 真值、真值航迹和评估误差只允许出现在明确标识的评估模式；
- 评估模式必须持续显示“仅供评估的真值”，并在截图和视频中可辨认；
- 模式切换不能改变后端控制输入或状态机，只改变展示层；
- 正式页面减少调试图层优先级，突出任务阶段、数据健康、owner 和阻塞原因。

个人验收效果：

- 正式运行帧和页面中不存在目标真值字段或真值图层；
- 评估页面可同时核对真值和公开估计，但有不可忽略的评估标识；
- 两种模式使用同一份公开执行状态，状态条结论一致。

## 5. 成员二：UUV 控制负责人

### 5.1 负责范围

主要涉及：

- `src/underwater_tracking/runtime/mission_controller.py`；
- `src/underwater_tracking/runtime/execution_coordinator.py`；
- `src/underwater_tracking/runtime/execution_evidence.py`；
- `src/underwater_tracking/simulation/engine.py`；
- `src/underwater_tracking/planning/coverage.py`；
- `src/underwater_tracking/planning/task_group_waypoints.py`；
- 三艇部署、运动、扫描、被动观测、状态迁移、owner、交接、替换、专属模式和退出相关测试。

UUV 控制层是物理执行和状态迁移的最终权威。任何 LLM 输出、世界模型预测或前端动作都不能绕过这里的部署、观测、邻接、安全距离和资源门限。

### 5.2 C-01：执行快照准入和过期恢复链路不闭合

**对应问题：I-01，负责确定性准入侧。**

修复建议：

- 审查 `valid_until_s` 到期前后的滚动检查、重校验、提交和 `MissionController` 应用链路；
- 新候选到达时按 scenario、base revision、execution revision、资源归属、几何和证据完整性原子校验；
- 当前快照过期或曾被标记为 terminal，不能永久阻止后续有效的更高 revision 提交；
- 提交失败时保留当前可审计状态，不得部分覆盖任务组、区域或 UUV 模式；
- 每次拒绝记录候选 revision、当前 revision、具体健康条件和是否成功恢复；
- 新快照应用时保留已经确认的扫描、跟踪和退出进度，不能把 live group 重置回初始状态。

个人验收效果：

- 正常长时运行中，在旧快照失效前接受更高 execution revision；
- 注入一次 `execution_snapshot_not_executable` 后，下一份满足条件的候选能够提交，状态从 expired/failed 恢复；
- revision 严格单调增加，HTTP、WebSocket、JSONL 和 Replay 一致；
- 任意提交失败都不会产生半更新、重复 owner、UUV 资源双重归属或任务组进度倒退。

### 5.3 C-02：融合估计未推进到 `PASSIVE_TRACK`

**对应问题：I-02。**

修复建议：

- 对每个观测周期记录并输出 `region_entry_probabilities`；
- 明确记录连续确认计数从 `0 -> 1 -> 2` 的变化；
- 当概率缺失、非有限、低于 `0.70` 或同周期判定目标离区时，将复位原因结构化输出；
- 检查主动扫描产生的初始接触是否进入“公开融合估计 -> 区域概率 -> `MissionController`”的同一链路；
- 只在连续两周期达到门限后，将整组三艇原子切换为 `PASSIVE_TRACK` 和被动传感器模式；
- 首个满足条件的被动组成为唯一 tracking owner；
- 禁止使用目标真值、规划时间窗或区域先验代替公开观测证据。

个人验收效果：

- seed `42` 普通运行中，实际出现的公开融合估计可以驱动至少一个区域连续两周期达到 `>= 0.70`；
- 同一组三艇在同一状态提交中全部切换为 `PASSIVE_TRACK`；
- 产生一次且仅一次对应的 `passive_track_started`，owner 非空且唯一；
- 若第二周期概率跌破门限，计数正确复位且保持 `ACTIVE_SCAN`；
- 任何验收数据都不从 `EvaluationFrame` 或目标物理真值进入状态机。

### 5.4 C-03：主动覆盖证据不足且与路线完成混淆

**对应问题：I-03。**

修复建议：

- 保证 `ACTIVE_SCAN` 三艇按定义的扫描路线循环执行，直到确认目标或本轮达到覆盖阈值；
- 主动模式必须按照配置的 ping 周期真实产生 source-backed `active_ping`；
- 由实际 ping 位置和有效作用范围累计本轮覆盖足迹，不能以访问航点数代替；
- 同时输出路线进度、轮次编号、主动覆盖率、source-backed ping 数和扫描完成布尔值；
- 覆盖重叠区域应按面积去重，扫描轮次切换时重置本轮统计；
- 保留当前简化声呐模型，不增加传播、多径、互扰或海况建模。

个人验收效果：

- 四个 `ACTIVE_SCAN` 区域均产生 source-backed 主动 ping，而不是只有一个区域产生一次；
- 覆盖率随真实 ping 足迹单调增加，路线完成不会直接把覆盖率改成 `100%`；
- 达到配置阈值时才输出 `scan_completed=true`；
- 重复 seed `42` 运行时扫描路线、ping 计数和覆盖摘要保持确定性一致；
- 三艇最小间距持续满足 `>= 300m` 安全门限。

### 5.5 C-04：区域交接闭环

**对应问题：I-05 的核心发布部分。**

修复建议：

- owner 预计离开当前区域时，仅选择相邻区域的三艇组作为候补；
- 候补组三艇必须全部已部署、健康且处于被动模式；
- 三艇必须各自提供同一有效观测周期的被动观测，不能只凭组级融合结果或历史观测通过；
- 条件未满足时保留旧 owner，并输出等待部署、等待被动观测或资源不可用原因；
- 条件满足时原子执行：新组成为 owner，旧 owner 进入 `EXITING`；
- 旧组完成边界退出后才进入 `DISAPPEARED` 并释放资源。

个人验收效果：

- 接班观测进度可观察到 `0/3 -> 1/3 -> 2/3 -> 3/3` 或直接从当周期证据确认 `3/3`；
- `tracking_owner_gap_frames = 0`；
- owner 切换帧中只有一个新 owner，旧组同时为 `EXITING`；
- 旧组越界前持续可见，越界后变为 `DISAPPEARED` 并释放三艇资源；
- 缺任意一艇有效被动观测时，handoff 必须保持 pending。

### 5.6 C-05：动态区域替换和专属跟踪恢复

**对应问题：I-05 的第二阶段演示。**

修复建议：

- 预测几何更新时保留每个区域槽位的一对 incoming/outgoing 组；
- 新组三艇完成部署和必要观测前，不删除旧组或转移 owner；
- 连续多个新 revision 到达时，同一槽位只保留最新合法替换；
- 专属模式只能锁定当前 owner 的完整三艇组；
- 任一成员剩余里程 `<= 7000m` 时进入 `DEDICATED_RELEASE_PENDING`；
- 新组三艇先形成有效被动跟踪并取得 owner，再恢复 `REGIONAL`，最后让旧专属组退出。

个人验收效果：

- 替换期间 incoming/outgoing 状态、批次和 revision 可审计，允许合法的短时新旧组并存；
- 不出现旧区域瞬间删除、UUV 瞬移、资源重复分配或旧 revision 覆盖新 revision；
- 专属组三艇始终同时保持被动模式；
- `7000m` 阈值触发后，新 owner 先接管，旧专属组后退出；
- 恢复后模式为 `REGIONAL`，旧组最终 `DISAPPEARED`。

### 5.7 C-06：补齐前端所需的权威状态字段

**对应问题：I-04。**

UUV 控制负责人需通过 `OperationalFrame` 提供或确认以下后端字段，前端不得自行计算：

- 每区域路线进度、扫描轮次、主动覆盖率、source-backed ping 数和扫描完成状态；
- `region_entry_probabilities`；
- 连续确认计数和要求周期数；
- 任务组生命周期、传感器模式、成员 ID、部署批次；
- tracking owner 和 pending successor；
- 接班组三艇各自的有效被动观测状态；
- incoming/outgoing 替换状态；
- 阻塞原因和相关证据 ID；
- execution revision、geometry revision、事件时间。

个人验收效果：同一 `OperationalFrame` 已足够让前端完整还原状态机叙事，不读取历史帧、不读真值、不在浏览器中重新实现决策规则。

## 6. 成员三：世界模型负责人

### 6.1 负责范围

主要涉及：

- `src/underwater_tracking/tracking/` 中公开目标估计、IMM 和区域概率所依赖的数据；
- `src/underwater_tracking/groups/` 中基于观测形成融合估计的链路；
- `src/underwater_tracking/world_model/` 中只读未来事件推演；
- 估计/预测的 revision、时间、新鲜度、质量和真值隔离契约。

世界模型没有物理控制权。它负责提供可信、及时、可解释的数据，不负责把任务组直接切换成 `PASSIVE_TRACK`，也不负责提交 UUV 航点。

### 6.2 W-01：公开融合估计和预测没有形成持续的新鲜数据流

**对应问题：I-01。**

修复建议：

- 检查主动扫描初始接触是否能进入统一的融合估计输入，而不是只生成一次孤立估计；
- 每次有满足质量条件的新观测时，更新 track revision、估计时间、均值、协方差和 source observation IDs；
- 同一轮公开估计必须生成同一 revision 的轨迹预测和世界模型事件；
- 没有新观测时按模型能力生成有界预测，并明确标记预测年龄和质量退化；
- 超过有效期时输出 `expired/unavailable`，不得将旧均值重新盖章为新估计；
- 公开链路中永久禁止读取物理目标真值。

个人验收效果：

- 在存在合格新观测的周期，公开估计的时间和 track revision 向前推进；
- 目标物理运动但长期无新观测时，页面收到的是明确的 stale/expired 状态，而不是伪造的 live estimate；
- 估计、IMM 预测和世界模型事件的 source track revision 一致；
- 相同 seed 和相同观测输入产生确定性一致的估计摘要。

### 6.3 W-02：为入区确认提供可审计的估计质量输入

**对应问题：I-02。**

修复建议：

- 向 UUV 控制层提供当前公开估计均值、二维协方差、估计时间、有效期和 source observation IDs；
- 对不可用、非有限、协方差非法或来源过期的估计明确拒绝，不让其进入区域概率计算；
- 保证“主动接触形成的初始估计”和后续被动估计采用同一公开轨迹契约；
- 区域概率的最终控制门限和连续计数仍由 UUV 控制层持有，世界模型只提供输入和质量说明；
- 对概率低的情况保留可解释依据，例如估计中心在区外或协方差质量不足。

个人验收效果：

- UUV 控制层能够仅凭公开估计计算所有四区概率，无需访问真值；
- 每个概率可以追溯到估计 revision、协方差和 source observation IDs；
- 估计失效时不会触发错误的 `2/2` 入区确认；
- 首次融合估计可以继续进入下一观测周期，而不是停留在单帧展示结果。

### 6.4 W-03：世界模型未来事件与执行状态保持一致

**对应问题：I-05。**

修复建议：

- 基于最新公开预测更新区域离开风险、覆盖缺口、几何退化和跟踪丢失风险；
- future event 必须携带 prediction revision、生成时间、有效期和 `control_authority: false`；
- 当预测过期时同步降级或撤下依赖该预测的未来事件；
- 世界模型可为 LLM decision maker 提供高层风险依据，但不能直接触发 owner 切换；
- 交接完成后，未来事件所引用的 owner/区域上下文必须更新到当前 revision。

个人验收效果：

- 页面上的预测线、H1-H4 事件和状态条引用同一 source track revision；
- 过期预测不会继续产生看似有效的未来事件；
- 世界模型输出中无目标真值、物理航点和控制命令；
- owner 切换后下一轮事件不再引用已退出的旧 owner 作为当前组。

### 6.5 W-04：真值只用于评估

**对应问题：I-06。**

修复建议：

- 保持 `OperationalFrame` 与 `EvaluationFrame` 分离；
- 正式公开估计、预测、区域概率、世界模型输入和 LLM prompt 均不得携带目标真值；
- 评估通道可计算估计误差，但必须有独立字段和显式模式标识；
- 增加契约测试，防止未来把 truth history、truth position 或 truth velocity 接回预测器。

个人验收效果：正式 HTTP、WebSocket、JSONL、Replay、世界模型输出和 LLM 输入均扫描不到目标真值字段；评估模式仍能单独计算并展示误差。

## 7. 成员四：LLM、多层记忆和智能助手负责人

### 7.1 负责范围

主要涉及：

- `src/underwater_tracking/agent/` 中后台规划循环和高层决策；
- `src/underwater_tracking/runtime/execution_snapshot_factory.py` 的候选生成接线；
- `src/underwater_tracking/memory/` 中多层记忆和事件凝练；
- 前端智能助手所消费的后端回答和证据引用；
- LLM 失败、超时、过期结果和确定性基线之间的降级边界。

`ExecutionCoordinator` 的提交准入由 UUV 控制负责人把关；本成员负责持续提供基于最新公开数据的候选，并保证 LLM 不成为物理闭环的单点故障。

### 7.2 L-01：快照过期前没有持续生成和提交新候选

**对应问题：I-01，负责候选生成侧。**

修复建议：

- 在当前 `valid_until_s` 前预留刷新窗口，主动启动下一轮 planning epoch；
- 每轮捕获不可变的 situation revision、公开 track revision 和 prediction revision；
- 旧 LLM 结果晚到时标记 stale 并丢弃，不能覆盖更高 revision；
- 新估计、新预测、区域链变化或快照即将到期都应形成可去重的重规划触发；
- 无 LLM、LLM 超时或语义优化失败时，先提交确定性合法基线；
- LLM 只允许对语义和高层策略做受限优化，不得修改物理安全字段；
- 记录每轮候选生成、验证、拒绝、重试和最终恢复结果。

个人验收效果：

- 正常长时运行不存在因等待 LLM 而跨过 `valid_until_s` 的执行 revision 空窗；
- 阻塞或关闭 LLM provider 后，确定性基线仍能按时刷新并保持 UUV 物理执行；
- 晚到的旧结果被拒绝且不会回滚 execution revision；
- 注入一次生成或提交失败后，系统在下一刷新周期使用最新公开数据重试并恢复；
- LLM 输出不能直接改变 UUV ID、物理航点、安全间距、owner 或状态机确认计数。

### 7.3 L-02：decision maker 与确定性状态机职责隔离

**对应问题：I-02、I-05。**

修复建议：

- `ACTIVE_SCAN -> PASSIVE_TRACK`、owner 切换、退出和 `7000m` 阈值判断全部留在确定性 UUV 状态机；
- LLM decision maker 只可提出区域模式/专属模式请求、优先级或语义优化候选；
- 每项高层建议必须携带 execution revision、frame ID、证据 ID 和有效期；
- 应用前由确定性校验器检查 revision、新鲜度、资源、邻接和观测条件；
- 拒绝 LLM 建议时保留当前安全计划，并给出结构化原因。

个人验收效果：

- 关闭 LLM 后，扫描、首次被动跟踪和相邻组交接仍可完成；
- LLM 给出越权或过期建议时，执行状态不改变且审计记录原因；
- 合法的专属模式请求只能在存在当前 passive owner 时被接受；
- LLM 不能通过文本建议绕过接班组 `3/3` 有效被动观测门限。

### 7.4 L-03：智能助手没有把关键阻塞状态解释给用户

**对应问题：I-04、I-06。**

修复建议：

- 助手回答直接引用当前 `OperationalFrame` 的 revision、数据年龄、状态机阶段和结构化阻塞原因；
- 能回答“目标为什么不动”“为什么仍在扫描”“为什么没有 owner”“为什么还未交接”；
- 明确区分路线完成、扫描覆盖完成、估计过期和仿真暂停；
- 不得根据截图外观或历史记忆推断当前状态；
- 回答中不得泄露评估真值，不得把世界模型规则置信度称为真实概率。

个人验收效果：

- 在过期估计帧上，助手说明估计已过期、最后更新时间、数据年龄和当前恢复状态；
- 在 `1/2` 入区确认帧上，助手说明仍缺一个连续观测周期；
- 在接班 `2/3` 帧上，助手能指出缺少哪一艘 UUV 的有效被动观测；
- 回答引用的 execution revision 和 frame ID 与当前页面一致。

### 7.5 L-04：多层记忆缺少本次闭环所需的审计语义

**对应问题：I-01、I-04、I-05。**

原始问题没有证明记忆检索算法本身错误，因此本项不要求重写多层记忆；只补齐支撑运行解释和复盘所需的结构化记录。

修复建议：

- 短期运行记忆记录最近的估计健康、区域概率、确认计数、覆盖进度和接班证据；
- 情节记忆凝练 `passive_track_started`、`tracking_ownership_transferred`、replacement、dedicated release 和 recovery；
- 长期记忆只保存经确认的处置经验，不保存高频物理帧和评估真值；
- 所有记忆条目携带 scenario、frame、execution revision、event/evidence ID 和时间；
- 过期快照拒绝和恢复应属于同一异常 episode，避免重复触发无限重规划。

个人验收效果：

- 能按一次运行重建“何时过期、为何拒绝、何时恢复、哪一 revision 生效”；
- 能重建首次跟踪和 owner 交接的证据链；
- 记忆不得成为控制输入的唯一事实来源，当前状态始终以实时 `OperationalFrame` 和权威执行快照为准；
- 重放同一运行不会重复生成相同转移事件或重复触发决策。

## 8. 四人之间必须统一的数据契约

| 数据/事件 | 生产主责 | 消费方 | 验收约束 |
| --- | --- | --- | --- |
| 公开融合估计、协方差、track revision、source observations | 世界模型 | UUV 控制、LLM、前端 | 无真值；时间和 revision 可追溯 |
| 预测轨迹、有效期、预测健康 | 世界模型 | LLM、UUV 控制、前端 | 与 source track revision 一致 |
| execution candidate | LLM/确定性规划链 | UUV 控制 | 只基于最新公开数据；带 base revision |
| 权威 execution snapshot | UUV 控制 | 前端、世界模型、LLM、记忆 | 原子提交；revision 单调；可恢复 |
| 区域概率与确认计数 | UUV 控制 | 前端、LLM 助手、记忆 | 每观测周期更新；原因可解释 |
| 主动覆盖和 source-backed ping | UUV 控制 | 前端、LLM 助手、记忆 | 不得用路线进度代替 |
| 组生命周期、owner、handoff evidence | UUV 控制 | 前端、世界模型、LLM、记忆 | owner 唯一；交接无空窗 |
| 世界模型未来事件 | 世界模型 | 前端、LLM | `control_authority: false`；随预测失效 |
| 助手解释 | LLM | 前端/用户 | 引用当前 frame/revision，不自行推断状态 |
| 评估真值 | 独立评估通道 | 评估页面/审计工具 | 禁止进入正式运行和控制链 |

所有跨模块字段最终应进入同一份 `OperationalFrame`，并在 HTTP、WebSocket、JSONL 和 Replay 中保持一致。若字段暂时缺失，应明确显示 unavailable，而不是由下游猜测。

## 9. 分阶段联调顺序

### 阶段 A：先恢复数据和执行活性

1. 世界模型负责人保证公开估计、预测、revision 和健康状态持续更新；
2. LLM 负责人保证确定性 baseline 在快照到期前生成，LLM 优化不阻塞刷新；
3. UUV 控制负责人保证更高 revision 可原子准入，过期状态可恢复；
4. 前端负责人完成 current/stale/expired 的诚实展示。

阶段验收：长时运行中不再永久停留在 `execution_snapshot_not_executable`，目标估计失效时页面不会伪装为 live，新 revision 到达后可恢复。

### 阶段 B：打通首次被动跟踪

1. 世界模型负责人交付可追溯的公开估计和协方差；
2. UUV 控制负责人输出四区概率、确认计数和复位原因，并完成 `PASSIVE_TRACK` 转移；
3. 前端负责人显示 `0/2 -> 1/2 -> 2/2 -> owner`；
4. LLM 助手负责人能解释当前阻塞原因，但不参与状态判定。

阶段验收：普通实时运行出现 `passive_track_started`，三艇同时被动，唯一 owner 非空。

### 阶段 C：完成真实扫描证据和相邻组交接

1. UUV 控制负责人完成四区真实主动 ping 和覆盖累计；
2. UUV 控制负责人完成候补组三艇 `3/3` 被动观测和无空窗 owner 切换；
3. 前端负责人完成覆盖、接班进度和退出过程展示；
4. 世界模型、LLM 和记忆同步更新到新 owner/revision。

阶段验收：同一固定 seed 普通运行中至少发生一次相邻组 owner 交接，`tracking_owner_gap_frames = 0`，旧组最终消失。

### 阶段 D：补齐替换和专属模式演示

1. 以真实仿真输入触发新预测 revision 和区域替换；
2. 以合法运行状态触发专属模式及 `7000m` 剩余里程门限；
3. 保存替换和专属恢复的后端帧、截图和事件日志；
4. 验证新组先接管、旧组后退出。

阶段验收：状态机夹具仍可用于回归测试，但最终证据必须来自实际 SimulationEngine、MissionController 和 `OperationalFrame` 链路。

## 10. 最终联合验收清单

### 10.1 核心发布门禁

使用 `configs/scenario/uuv_only_single_target.yaml`、seed `42` 进行重复两次的普通实时运行。运行时长应覆盖首次相邻区域交接；建议把自动验收上限设为 `3600 s`，若在上限内未交接则判失败并输出阻塞原因。

必须同时满足：

- 两次运行的物理轨迹、关键状态事件和覆盖摘要确定性一致；
- 12 艘 UUV、4 个初始三艇组均部署，组内成员互斥；
- 四区均有 source-backed 主动 ping，覆盖率和路线进度分别统计；
- 公开目标估计在有合格观测时持续更新，断流时明确降级或过期；
- 正常条件下 execution revision 在快照到期前滚动更新；
- 至少一个区域出现连续确认 `0/2 -> 1/2 -> 2/2`；
- 三艇原子进入 `PASSIVE_TRACK`，唯一 owner 非空；
- 相邻组三艇全部形成有效被动观测后完成 owner 切换；
- `tracking_owner_gap_frames = 0`；
- 旧 owner 先 `EXITING`，越界后 `DISAPPEARED`；
- 全程 UUV 最小间距不低于 `300m`；
- 正式 `OperationalFrame`、HTTP、WebSocket、JSONL、Replay 和页面无目标真值；
- 页面能区分仿真运行、估计过期、规划阻塞和任务暂停；
- 保存扫描、首次跟踪和接力三张真实关键帧及对应原始帧 JSON。

### 10.2 第二阶段演示门禁

必须补充：

- 一次动态区域替换：incoming/outgoing 并存，新 revision 生效，旧组越界消失；
- 一次专属跟踪恢复：当前 owner 进入 `DEDICATED_TRACK`，剩余里程到门限后新组先接管，系统恢复 `REGIONAL`；
- 保存替换和专属恢复关键帧、原始帧 JSON、事件日志和运行 manifest；
- 截图中的所有状态均可在同期 `OperationalFrame` 中逐字段核对。

### 10.3 故障恢复门禁

至少注入并通过以下故障测试：

- 一次快照过期或候选拒绝：记录原因并在后续有效 revision 到达时恢复；
- 一次 LLM 超时/不可用：确定性规划和物理状态机继续运行；
- 一次入区确认中断：计数正确复位，不误进入被动跟踪；
- 一次接班缺少一艇观测：旧 owner 保持，补齐 `3/3` 后再切换；
- 一次过期预测：前端和助手均标记失效，不显示为 live，不使用真值补偿。

## 11. 每位成员提交验收材料

每位成员提交材料时统一包含：

- 修改文件列表和职责说明；
- 新增/修改的数据字段及生产者、消费者；
- 单元测试和集成测试命令及结果；
- 一份使用同一 frame ID 和 execution revision 的后端 JSON 与前端截图对照；
- 失败路径测试及结构化拒绝原因；
- 对正式链路无目标真值的说明；
- 未完成项和对其他成员的接口依赖。

个人部分“通过”不等于项目完成。只有四人的交付在第 10 节联合验收中同时成立，才能认定整个算法达到最终效果。

## 12. 明确不在本轮范围内的内容

本轮不实现：

- 主动声呐互扰；
- 海洋声传播；
- 多径；
- 通信时延；
- 海况影响；
- 武器链；
- LLM 直接生成坐标、航点或物理控制命令；
- 用物理目标真值推进正式状态机；
- 以合成夹具截图代替普通实时仿真证据。

保持这些边界，才能把本轮资源集中在“持续估计、真实覆盖、首次被动跟踪、唯一 owner、无缝交接和诚实可视化”这一条最终闭环上。
