# 三艇动态跟踪后端状态机工作蓝图

## 1. 文档目的

本文用较直观的语言说明三艇动态跟踪方案是如何生成和推演的，重点解释后端状态机的工作逻辑。

这套方案不是一次性计算一条固定路线，而是持续执行下面的闭环：

```text
目标预测
  -> 生成区域和三艇任务组
  -> 仿真环境执行运动和探测
  -> 后端读取观测结果
  -> 更新任务状态和跟踪所有权
  -> 必要时生成新的区域替换方案
  -> 继续下一轮推演
```

## 2. 后端和仿真各自负责什么

### 仿真环境负责物理过程

仿真引擎负责模拟实际发生的事情：

- 移动目标；
- 按任务路径移动 UUV；
- 计算 UUV 的位置、里程和能量变化；
- 判断 UUV 是否完成部署、是否到达区域边界；
- 生成主动探测和被动探测结果。

### 后端状态机负责任务决策

后端不直接移动 UUV，也不把 UUV 瞬移到新区域。它根据仿真或真实系统传来的观测，判断：

- 三艇是否已经全部部署；
- 任务组是否可以开始扫描或被动跟踪；
- 目标是否已经进入某个区域；
- 是否满足跟踪所有权交接条件；
- 旧任务组是否真的越过边界；
- 是否需要替换区域或触发专属跟踪模式；
- 某个 UUV 或区域是否已经降级、需要恢复。

仿真引擎可以使用真实位置计算探测结果，但后端状态机只使用已经产生的观测结果推进状态。这样可以验证方案是否真的能够运行，而不是直接读取答案。

## 3. 初始跟踪方案如何生成

后端首先接收以下输入：

- 目标当前位置和历史轨迹；
- 目标未来轨迹预测；
- 目标意图和预测可信度；
- UUV 的位置、能量、里程和健康状态；
- 当前跟踪策略参数。

然后围绕目标预测路线生成四个连续的动态区域。每个区域是一个 `2000m x 2000m` 的正方形。

每个区域绑定一个三艇任务组：

```text
区域 1 -> 三艇任务组 1
区域 2 -> 三艇任务组 2
区域 3 -> 三艇任务组 3
区域 4 -> 三艇任务组 4
```

初始方案一共包含 4 个任务组和 12 艘 UUV。每个任务组保存自己的三艇 ID、部署批次、所属区域、当前生命周期和传感器模式。

方案还会记录一个版本号。新的预测或新的区域几何只能通过更高版本的方案进入执行流程，不能直接覆盖当前正在执行的方案。

## 4. 三层状态要同时保持一致

后端不是只维护一个状态，而是同时维护三层状态：

| 状态层 | 说明 |
| --- | --- |
| 区域状态 | 这个区域是否正在部署、扫描、跟踪、交接或恢复 |
| 任务组状态 | 这个三艇小组是否正在进入、扫描、被动跟踪、退出或已经消失 |
| UUV 资源状态 | 每艘 UUV 的部署状态、能量、里程、健康度和资源批次 |

另外还有一项目标级状态：当前由哪个三艇任务组拥有目标跟踪所有权，以及是否正在等待后继组接管。

## 5. 普通区域跟踪，也就是模式 1

一个三艇任务组的主要生命周期如下：

```text
ENTERING
    -> ACTIVE_SCAN
    -> PASSIVE_TRACK
    -> EXITING
    -> DISAPPEARED
```

### 5.1 进入区域并主动扫描

初始任务组先处于 `ENTERING`。当三艇全部到达各自区域并被观测为已部署后：

1. 区域进入主动扫描阶段；
2. 任务组变为 `ACTIVE_SCAN`；
3. 三艇全部使用主动探测；
4. 三艇同步执行同一个任务组的扫描任务。

不完整的三艇组不能进入水中执行，也不能成为跟踪所有者。

### 5.2 从主动扫描转为被动跟踪

当目标进入某个区域时，后端不会只依据一次判断立即切换。当前策略要求：

- 目标进入概率达到 `0.70`；
- 连续两个观测周期都满足条件；
- 没有同时出现目标已经离开该区域的判断。

确认成功后，整组三艇原子地从主动扫描切换到 `PASSIVE_TRACK`，三艇全部使用被动探测。

### 5.3 区域之间的跟踪交接

当前被动跟踪小组成为目标的 tracking owner。目标向下一个区域移动时，后继小组必须先证明自己能够接管：

- 后继区域必须是相邻区域；
- 后继组三艇必须全部已经部署；
- 后继组三艇必须全部产生有效被动观测。

如果任一条件不满足，后端只记录“等待被动观测”或“等待部署”，不会释放当前 owner。

条件全部满足后，状态变化如下：

```text
后继组三艇完成被动观测
          -> 后继组成为新的 tracking owner
          -> 原 owner 变为 EXITING
          -> 新 owner 继续被动跟踪
          -> 原组三艇越过边界
          -> 原组变为 DISAPPEARED
```

这里的顺序很重要：先让新组三艇接管，再让旧组三艇退出，避免目标在交接过程中失去跟踪。

## 6. 预测变化时如何动态替换区域

目标预测会不断刷新，区域的中心位置或几何版本也可能变化。后端不会把正在执行的旧区域立即删除，而是建立一个有过渡过程的替换：

```text
旧区域和旧任务组
        -> 新区域和新任务组生成
        -> 旧组与新组同时存在
        -> 新组三艇完成部署和观测
        -> 新组接管
        -> 旧组三艇到达退出边界
        -> 旧组消失并释放资源
```

每个固定区域槽位最多保留一对任务组：

- `outgoing`：正在退出的旧组；
- `incoming`：正在进入的新组。

如果短时间内连续收到多个新区域版本，同一个区域槽位只保留最新版本，避免旧方案反复覆盖新方案。

替换期间最多可能同时存在 8 个任务组，也就是 24 艘可见 UUV。旧组只有在收到边界退出观测后才会真正从运行状态中移除。

旧组消失后，其三艇资源立即重置为可重新部署状态：

- 部署状态回到 `ONBOARD`；
- 里程清零；
- 能量恢复为满值；
- 健康和能力恢复；
- 资源批次号递增。

## 7. 模式 2：专属三艇跟踪

模式 2 只能锁定当前正在被动跟踪目标的 owner 三艇组，不能临时从不同任务组中拼接 UUV。

其生命周期如下：

```text
PASSIVE_TRACK
        -> DEDICATED_TRACK
        -> DEDICATED_RELEASE_PENDING
        -> 新三艇组形成有效被动跟踪
        -> 新组接管所有权
        -> 恢复 REGIONAL 模式
```

进入模式 2 后：

1. 当前 owner 的三艇被锁定为专属跟踪组；
2. 三艇全部持续使用被动探测；
3. 不执行普通区域交接；
4. 不允许手工提前释放专属组。

当专属组三艇中任意一艇的剩余里程小于等于 `7000m` 时，后端触发整组三艇更换：

1. 当前专属组进入 `DEDICATED_RELEASE_PENDING`；
2. 根据最新的四个区域生成新的四个三艇组；
3. 当前目标区域的新组三艇先完成部署和被动观测；
4. 新组成为 tracking owner；
5. 系统恢复为普通 `REGIONAL` 模式；
6. 旧专属组三艇再从边界退出并释放资源。

这保证了专属跟踪更换过程中不会直接丢失目标。

## 8. 每个仿真周期后端如何推进状态

每个观测周期都执行一次类似下面的流程：

```text
接收并整理观测
  -> 更新 UUV 里程、能量和健康状态
  -> 处理故障和降级
  -> 检查模式 2 的里程阈值
  -> 处理任务组消失和区域替换
  -> 处理三艇部署完成
  -> 处理目标进入区域的连续确认
  -> 处理 tracking owner 和区域交接
  -> 处理返航、恢复和边界退出
  -> 记录外部事件
  -> 生成最新执行状态
```

如果观测不完整，状态机停留在当前阶段或进入等待/降级状态，不会假设任务已经完成。例如，后继组三艇只有两艇产生被动观测时，交接不会成功。

## 9. 新方案如何进入正在运行的系统

新的预测方案先生成一个新的执行版本，然后经过版本检查：


- 方案必须属于当前场景；
- 执行版本必须比当前版本更新；
- 必须包含完整的四区域和三艇任务组；
- 不能破坏当前已经确认的物理资源归属。

检查通过后，后端以原子方式应用新方案。如果应用失败，整个控制器恢复到应用前的状态，当前有效方案继续执行。

这样，预测刷新不会把运行中的任务变成半更新状态。

## 10. 状态如何提供给前端和回放

每轮状态推进后，后端生成一份完整的执行状态，包含：

- 目标状态；
- 四个区域及其几何版本；
- 每个三艇任务组的生命周期和传感器模式；
- 每艘 UUV 的位置、模式和资源状态；
- 当前 tracking owner；
- 正在进行的区域替换；
- 已发生的结构化事件；
- 当前执行版本。

HTTP、WebSocket、Replay 和前端都使用同一份 `OperationalFrame`。前端只负责显示后端已经确认的状态，不在浏览器中重新推断一套状态机。

## 11. 整体逻辑总结

这套动态跟踪算法可以概括为四句话：

1. 预测结果负责提出“目标可能经过哪些区域，以及三艇应该如何布置”。
2. 仿真环境负责执行 UUV 和目标的实际运动，并产生探测观测。
3. 后端状态机负责根据观测决定“现在能否进入下一阶段”。
4. 任何交接、替换和资源释放，都必须先满足对应的观测条件。

因此，系统的主逻辑不是“重新计算后立即替换”，而是：

```text
先生成 -> 再执行 -> 读取观测 -> 确认状态 -> 平滑交接 -> 释放旧资源 -> 继续跟踪
```
